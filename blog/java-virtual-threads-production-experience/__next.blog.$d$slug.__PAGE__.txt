f:T275f,<p>Virtual threads are one of those platform changes that don&#39;t just tweak Java — they change how you think about building services.</p>
<p>When Project Loom landed in Java 21, many of us had the same reaction:</p>
<p><strong>&quot;Wait… I can write blocking code again and still scale?&quot;</strong></p>
<p>Yes — mostly. But as always, production has a way of stress-testing every abstraction.</p>
<p>Some teams saw immediate wins. Others (Netflix included) ran into a subtle but serious edge case called <strong>thread pinning</strong> that could quietly stall services under load.</p>
<p>The good news: the root issue was fixed in Java 24 — and with Java 25 now the LTS, virtual threads are finally at a point where adoption makes sense for both engineers and engineering leaders.</p>
<p>This post is written for people who care about how systems behave after launch, not just how clean the code looks.</p>
<h2>The Mental Model That Actually Matters</h2>
<p>A virtual thread is <strong>not</strong> a lightweight OS thread.</p>
<p>The model that works in practice is:</p>
<ul>
<li><strong>Virtual threads are scheduled by the JVM</strong></li>
<li><strong>They run on a limited pool of real OS threads called carrier threads</strong></li>
<li><strong>When a virtual thread blocks on I/O, it usually steps aside</strong></li>
<li><strong>The carrier thread is immediately reused</strong></li>
</ul>
<p>That&#39;s the key idea: <strong>blocking code without blocking the OS</strong>.</p>
<pre><code class="language-java">try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -&gt; handleRequest());
}
</code></pre>
<p>You can create a lot of these — hundreds of thousands or more — without the JVM falling over.</p>
<p>That&#39;s fundamentally different from traditional thread pools.</p>
<h2>Virtual Threads with Spring Boot (This Part Is Refreshingly Boring)</h2>
<p>Spring Boot made virtual threads almost trivial to turn on — which is exactly what you want.</p>
<p><strong>Enable virtual threads:</strong></p>
<pre><code class="language-yaml">spring:
  threads:
    virtual:
      enabled: true
</code></pre>
<p>Once enabled:</p>
<ul>
<li>Each incoming HTTP request runs on a virtual thread</li>
<li>Controllers and services stay synchronous</li>
<li>No reactive rewrite</li>
<li>No callback gymnastics</li>
</ul>
<p><strong>A plain Spring MVC controller — unchanged:</strong></p>
<pre><code class="language-java">@RestController
@RequestMapping(&quot;/orders&quot;)
public class OrderController {
    
    private final OrderService service;
    
    public OrderController(OrderService service) {
        this.service = service;
    }
    
    @GetMapping(&quot;/{id}&quot;)
    public Order getOrder(@PathVariable String id) {
        return service.getOrder(id); // blocking DB call is fine
    }
}
</code></pre>
<p>From a code readability standpoint, nothing changed. From a scalability standpoint, everything did.</p>
<p>And then people started running this under real traffic.</p>
<h2>The Sharp Edge Teams Ran Into: Thread Pinning</h2>
<p>Thread pinning is one of those issues you don&#39;t notice — until it hurts badly.</p>
<p>It happens when a virtual thread <strong>cannot detach</strong> from its carrier thread.</p>
<p>When that happens:</p>
<ul>
<li>The carrier thread is stuck</li>
<li>Enough pinned virtual threads → no free carriers</li>
<li>Requests stop making progress</li>
<li>CPU usage stays deceptively low</li>
<li>Latency graphs look catastrophic</li>
</ul>
<p>That combination made the problem especially hard to diagnose.</p>
<h3>The Most Common Way Teams Accidentally Pinned Threads</h3>
<p><strong>Blocking while holding a synchronized lock.</strong></p>
<p>Here&#39;s a simplified example that looks perfectly reasonable:</p>
<pre><code class="language-java">@Service
public class InventoryService {
    
    private final Map&lt;String, Integer&gt; cache = new HashMap&lt;&gt;();
    
    // ❌ problematic with virtual threads (Java 21–23)
    public synchronized int getInventory(String sku) {
        return cache.computeIfAbsent(sku, this::loadFromDb);
    }
    
    private int loadFromDb(String sku) {
        return jdbcTemplate.queryForObject(
            &quot;select qty from inventory where sku = ?&quot;,
            Integer.class,
            sku
        );
    }
}
</code></pre>
<p><strong>What&#39;s really happening:</strong></p>
<ol>
<li><code>synchronized</code> uses JVM monitors</li>
<li>A virtual thread enters the monitor</li>
<li>JDBC blocks while the monitor is held</li>
<li>The JVM pins the virtual thread to its carrier</li>
<li>That carrier can&#39;t run anything else</li>
</ol>
<p>Under enough traffic, you exhaust carriers. The service doesn&#39;t crash — it just stops responding.</p>
<h2>Netflix&#39;s Experience (And Why It Matters)</h2>
<p>Netflix adopted virtual threads early and ran into exactly this failure mode in production.</p>
<p><strong>The symptoms were confusing:</strong></p>
<ul>
<li>Requests appeared &quot;hung&quot;</li>
<li>Thread dumps showed plenty of virtual threads</li>
<li>CPU usage wasn&#39;t high</li>
<li>Scaling thread pools didn&#39;t help</li>
</ul>
<p>After investigation, Netflix traced the issue back to <code>synchronized</code> blocks combined with blocking I/O, which caused virtual threads to pin and exhaust carrier threads.</p>
<h3>How Netflix Handled It (Pre–Java 24)</h3>
<p>Netflix didn&#39;t abandon virtual threads. Instead, they:</p>
<p><strong>Refactored synchronized hot spots:</strong></p>
<ul>
<li>Replaced <code>synchronized</code> with <code>ReentrantLock</code></li>
<li>Reduced lock scope</li>
<li>Avoided blocking while holding locks</li>
</ul>
<p><strong>Instrumented aggressively:</strong></p>
<ul>
<li>Used Java Flight Recorder (JFR) events like <code>VirtualThreadPinned</code> to find problem areas</li>
</ul>
<p><strong>Rolled out selectively:</strong></p>
<ul>
<li>Virtual threads only where code paths and libraries were well understood</li>
</ul>
<p>Netflix documented this journey publicly and shared their learnings with the Java community — which directly influenced improvements in the JVM.</p>
<p>👉 <strong>If you want to read the original Netflix write-up, it&#39;s here:</strong> <a href="https://netflixtechblog.com/java-21-virtual-threads-dude-wheres-my-lock-3052540e231d">&quot;Java 21 Virtual Threads – Dude, Where&#39;s My Lock?&quot;</a></p>
<p>Full credit to the Netflix engineering team for being transparent about what broke and why — the ecosystem is better because of it.</p>
<h2>The Workaround Most Teams Used Before Java 24</h2>
<p>Here&#39;s the safer version of the earlier example:</p>
<pre><code class="language-java">@Service
public class InventoryService {
    
    private final Map&lt;String, Integer&gt; cache = new HashMap&lt;&gt;();
    private final Lock lock = new ReentrantLock();
    
    public int getInventory(String sku) {
        Integer cached;
        
        lock.lock();
        try {
            cached = cache.get(sku);
        } finally {
            lock.unlock();
        }
        
        if (cached != null) {
            return cached;
        }
        
        // blocking happens outside the lock
        int qty = loadFromDb(sku);
        
        lock.lock();
        try {
            cache.put(sku, qty);
        } finally {
            lock.unlock();
        }
        
        return qty;
    }
}
</code></pre>
<p>This works. It avoids pinning. It also adds complexity that many teams didn&#39;t love spreading across large codebases.</p>
<h2>What Changed in Java 24 — And Why Java 25 Is the Real Inflection Point</h2>
<p>Java 24 introduced <strong>JEP 491</strong>, which fundamentally changed how <code>synchronized</code> interacts with virtual threads.</p>
<p><strong>In short:</strong></p>
<ul>
<li>Monitors are no longer tied to carrier threads</li>
<li>Virtual threads can block while holding a monitor</li>
<li>Carrier threads are free to run other work</li>
<li>The most common pinning scenario disappears</li>
</ul>
<p>That means this code:</p>
<pre><code class="language-java">public synchronized Order load(String id) {
    return repository.findById(id);
}
</code></pre>
<ul>
<li>❌ risky in Java 21–23</li>
<li>✅ generally safe starting in Java 24</li>
<li>✅ safe and LTS-backed in Java 25</li>
</ul>
<p>This matters because <strong>Java 25 is the first LTS where virtual threads are both stable and safe by default</strong>.</p>
<p>There are still edge cases (native code, JNI), but the biggest foot-gun is gone.</p>
<h2>What This Means for Engineers and Engineering Leaders</h2>
<p>A few grounded takeaways:</p>
<ul>
<li><strong>Java 21</strong> made virtual threads usable</li>
<li><strong>Java 24</strong> fixed the most dangerous behavior</li>
<li><strong>Java 25</strong> makes virtual threads an LTS-safe default</li>
<li><strong>Spring Boot</strong> makes adoption trivial</li>
<li><strong>Observability</strong> still matters</li>
<li><strong>You don&#39;t need to rewrite your architecture</strong> to benefit</li>
</ul>
<p>The risk profile has shifted meaningfully.</p>
<p>What felt &quot;cool but scary&quot; a year ago now feels… reasonable.</p>
<h2>Final Thought</h2>
<p>Virtual threads aren&#39;t about squeezing more threads into the JVM.</p>
<p>They&#39;re about:</p>
<ul>
<li><strong>Returning to simple, readable, synchronous code</strong></li>
<li><strong>Scaling I/O-heavy services without reactive complexity</strong></li>
<li><strong>Avoiding architectural contortions we all learned to tolerate</strong></li>
</ul>
<p>With Java 25 as LTS — and lessons from teams like Netflix baked into the platform — this finally feels like the right moment.</p>
<p>If you&#39;ve been watching Loom from the sidelines, now&#39;s the time to step in.</p>
