Java Virtual Threads in the Real World: What Worked, What Broke, and Why Java 25 Is the Right Time to Adopt

Pradeep Renukaiah
December 22, 2025
7 min read

Virtual threads are one of those platform changes that don't just tweak Java — they change how you think about building services. Learn from production experiences, including Netflix's journey, and why Java 25 makes adoption finally safe.

Virtual threads are one of those platform changes that don't just tweak Java — they change how you think about building services.

When Project Loom landed in Java 21, many of us had the same reaction:

"Wait… I can write blocking code again and still scale?"

Yes — mostly. But as always, production has a way of stress-testing every abstraction.

Some teams saw immediate wins. Others (Netflix included) ran into a subtle but serious edge case called thread pinning that could quietly stall services under load.

The good news: the root issue was fixed in Java 24 — and with Java 25 now the LTS, virtual threads are finally at a point where adoption makes sense for both engineers and engineering leaders.

This post is written for people who care about how systems behave after launch, not just how clean the code looks.

The Mental Model That Actually Matters

A virtual thread is not a lightweight OS thread.

The model that works in practice is:

  • Virtual threads are scheduled by the JVM
  • They run on a limited pool of real OS threads called carrier threads
  • When a virtual thread blocks on I/O, it usually steps aside
  • The carrier thread is immediately reused

That's the key idea: blocking code without blocking the OS.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> handleRequest());
}

You can create a lot of these — hundreds of thousands or more — without the JVM falling over.

That's fundamentally different from traditional thread pools.

Virtual Threads with Spring Boot (This Part Is Refreshingly Boring)

Spring Boot made virtual threads almost trivial to turn on — which is exactly what you want.

Enable virtual threads:

spring:
  threads:
    virtual:
      enabled: true

Once enabled:

  • Each incoming HTTP request runs on a virtual thread
  • Controllers and services stay synchronous
  • No reactive rewrite
  • No callback gymnastics

A plain Spring MVC controller — unchanged:

@RestController
@RequestMapping("/orders")
public class OrderController {
    
    private final OrderService service;
    
    public OrderController(OrderService service) {
        this.service = service;
    }
    
    @GetMapping("/{id}")
    public Order getOrder(@PathVariable String id) {
        return service.getOrder(id); // blocking DB call is fine
    }
}

From a code readability standpoint, nothing changed. From a scalability standpoint, everything did.

And then people started running this under real traffic.

The Sharp Edge Teams Ran Into: Thread Pinning

Thread pinning is one of those issues you don't notice — until it hurts badly.

It happens when a virtual thread cannot detach from its carrier thread.

When that happens:

  • The carrier thread is stuck
  • Enough pinned virtual threads → no free carriers
  • Requests stop making progress
  • CPU usage stays deceptively low
  • Latency graphs look catastrophic

That combination made the problem especially hard to diagnose.

The Most Common Way Teams Accidentally Pinned Threads

Blocking while holding a synchronized lock.

Here's a simplified example that looks perfectly reasonable:

@Service
public class InventoryService {
    
    private final Map<String, Integer> cache = new HashMap<>();
    
    // ❌ problematic with virtual threads (Java 21–23)
    public synchronized int getInventory(String sku) {
        return cache.computeIfAbsent(sku, this::loadFromDb);
    }
    
    private int loadFromDb(String sku) {
        return jdbcTemplate.queryForObject(
            "select qty from inventory where sku = ?",
            Integer.class,
            sku
        );
    }
}

What's really happening:

  1. synchronized uses JVM monitors
  2. A virtual thread enters the monitor
  3. JDBC blocks while the monitor is held
  4. The JVM pins the virtual thread to its carrier
  5. That carrier can't run anything else

Under enough traffic, you exhaust carriers. The service doesn't crash — it just stops responding.

Netflix's Experience (And Why It Matters)

Netflix adopted virtual threads early and ran into exactly this failure mode in production.

The symptoms were confusing:

  • Requests appeared "hung"
  • Thread dumps showed plenty of virtual threads
  • CPU usage wasn't high
  • Scaling thread pools didn't help

After investigation, Netflix traced the issue back to synchronized blocks combined with blocking I/O, which caused virtual threads to pin and exhaust carrier threads.

How Netflix Handled It (Pre–Java 24)

Netflix didn't abandon virtual threads. Instead, they:

Refactored synchronized hot spots:

  • Replaced synchronized with ReentrantLock
  • Reduced lock scope
  • Avoided blocking while holding locks

Instrumented aggressively:

  • Used Java Flight Recorder (JFR) events like VirtualThreadPinned to find problem areas

Rolled out selectively:

  • Virtual threads only where code paths and libraries were well understood

Netflix documented this journey publicly and shared their learnings with the Java community — which directly influenced improvements in the JVM.

👉 If you want to read the original Netflix write-up, it's here: "Java 21 Virtual Threads – Dude, Where's My Lock?"

Full credit to the Netflix engineering team for being transparent about what broke and why — the ecosystem is better because of it.

The Workaround Most Teams Used Before Java 24

Here's the safer version of the earlier example:

@Service
public class InventoryService {
    
    private final Map<String, Integer> cache = new HashMap<>();
    private final Lock lock = new ReentrantLock();
    
    public int getInventory(String sku) {
        Integer cached;
        
        lock.lock();
        try {
            cached = cache.get(sku);
        } finally {
            lock.unlock();
        }
        
        if (cached != null) {
            return cached;
        }
        
        // blocking happens outside the lock
        int qty = loadFromDb(sku);
        
        lock.lock();
        try {
            cache.put(sku, qty);
        } finally {
            lock.unlock();
        }
        
        return qty;
    }
}

This works. It avoids pinning. It also adds complexity that many teams didn't love spreading across large codebases.

What Changed in Java 24 — And Why Java 25 Is the Real Inflection Point

Java 24 introduced JEP 491, which fundamentally changed how synchronized interacts with virtual threads.

In short:

  • Monitors are no longer tied to carrier threads
  • Virtual threads can block while holding a monitor
  • Carrier threads are free to run other work
  • The most common pinning scenario disappears

That means this code:

public synchronized Order load(String id) {
    return repository.findById(id);
}
  • ❌ risky in Java 21–23
  • ✅ generally safe starting in Java 24
  • ✅ safe and LTS-backed in Java 25

This matters because Java 25 is the first LTS where virtual threads are both stable and safe by default.

There are still edge cases (native code, JNI), but the biggest foot-gun is gone.

What This Means for Engineers and Engineering Leaders

A few grounded takeaways:

  • Java 21 made virtual threads usable
  • Java 24 fixed the most dangerous behavior
  • Java 25 makes virtual threads an LTS-safe default
  • Spring Boot makes adoption trivial
  • Observability still matters
  • You don't need to rewrite your architecture to benefit

The risk profile has shifted meaningfully.

What felt "cool but scary" a year ago now feels… reasonable.

Final Thought

Virtual threads aren't about squeezing more threads into the JVM.

They're about:

  • Returning to simple, readable, synchronous code
  • Scaling I/O-heavy services without reactive complexity
  • Avoiding architectural contortions we all learned to tolerate

With Java 25 as LTS — and lessons from teams like Netflix baked into the platform — this finally feels like the right moment.

If you've been watching Loom from the sidelines, now's the time to step in.
